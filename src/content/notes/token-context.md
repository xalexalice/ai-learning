## 要解决的问题

写提示时，字符数能否直接当作模型输入长度？不能。Token 是分词器产生的单位，可能对应词、子词或更细的片段；它与“字数”的关系需要针对所用分词器确认。

## 我的理解

Hugging Face 的课程把编码分成文本切分与 ID 转换。我的工程理解是：长度预算应绑定模型版本，而不是凭中文字符数估计。先列出系统指令、用户问题、历史消息和检索资料，再为输出留空间。

具体上下文上限需要查阅选用模型或服务的文档。本站不提供通用的字符换算比例，也不把某个模型的限制推广到所有模型。

## 示例与验证

可以先画一张预算表，列出各类输入的来源和可删减顺序。这个例子只用于设计思考；真实 token 数仍应使用目标分词器测量，本笔记没有运行模型分词实验。

| 输入部分 | 需要保留什么 | 预算紧张时如何处理 |
| --- | --- | --- |
| 用户问题 | 当前任务与限制 | 精简重复表达 |
| 对话历史 | 仍影响答案的信息 | 先检查过期内容 |
| 检索资料 | 可支持答案的证据 | 去重并保留来源 |

## 适用边界与反例

减少 token 不必然改善答案。如果删掉关键约束或证据，输入更短也可能更差。生成长度与模型输入长度还要分别理解；Transformers 的 `max_new_tokens` 定义不应直接套到其他服务。

2. 你会优先压缩哪部分输入，怎样确认没有丢掉关键证据？
